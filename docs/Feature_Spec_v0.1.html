Feature Specification — v0.1

How 2-second position samples become model inputs for the XGBoost classifier in the proposal. Scope is deliberately unchanged; the priority is getting the leakage handling right.

Status: draft, nothing here is decided yet. This is the piece the mentor flagged as unspecified ("decide how raw position time series become tabular features"). Numbers below are measured from the 20-match pilot; thresholds are proposals that should be validated against the parsed data before we commit.

This document stays inside the approved plan — movement features into an XGBoost skill classifier with SHAP. Two ideas that would change the modelling setup itself are deliberately kept out and written up separately in Feature Spec — Extensions, so that adopting them stays a separate decision. Section 6 is the part that matters most: there is a leakage route that affects the existing plan regardless of which extensions we do or do not take.

1. What we actually have

Parsing produces exactly one table. Everything in this spec is derived from it:

match_id   tick   sec    player   player_slot   x        y
8912186878    0    0.0        0             0   9515.2   9975.4
8912186878    0    0.0        5           128  23451.8  22746.1
8912186878   60    2.0        0             0   9702.6  10140.3
...

One row per player per 2 seconds — about 12,000 rows and 0.15 MB per match. It joins to a player table carrying account_id, hero_id, rank_tier and leaver_status.

What we do not have yet: facing angle, action state, health, and combat events (kills, deaths, tower and Roshan). These need a second extraction pass. Because the raw replays are archived, adding them later costs about 14 seconds per match rather than a re-collection — but any feature depending on them cannot be built today.

2. Two derived tables, not one

The model needs one row per player per match. Going straight there from raw positions in a single step is possible but awkward: nearly every aggregate depends on the same intermediate quantities — how far forward the player is, which zone they are in, how far from teammates — and recomputing those inside each aggregation is where mistakes hide.

So the spec defines an intermediate table first. It is a per-timestep view with those quantities already resolved, and the model table is a plain groupby over it:

LayerShapeWhat it isServes
L0player × 2 sRaw sampled positions — what parsing already gives usEverything downstream
L1player × 2 sPer-step quantities resolved once, in a team-relative frameEDA, trajectory plots, sanity checks
L2player × matchAggregates over zone × phase bucketsXGBoost + SHAP (the committed MVP)
Why bother with L1. It makes L2 a groupby instead of a pile of bespoke calculations, it is the table you want for trajectory plots and heatmaps in the report, and it is where the coordinate transform below is applied once rather than repeatedly. It also happens to be the shape any later modelling extension would need, but that is a side effect, not the reason.

3. The coordinate transform (do this before anything else)

Raw x, y cannot be used directly. Radiant spawns at low coordinates, Dire at high ones. The same numeric position means opposite things for the two teams — "deep in enemy territory" is a high x for Radiant and a low x for Dire. Feed raw coordinates to a model and the first thing it learns is which team you were on. Every feature below is computed in a team-relative frame instead.

The pilot gives us the two landmarks we need. Averaged over the first sampled tick of each match, the Radiant fountain sits at about (9515, 9975) and the Dire fountain at about (23451, 22746). That line is the map's main diagonal — the mid lane — and it defines a natural frame:

R = (9515, 9975)          Radiant fountain
D = (23451, 22746)        Dire fountain
axis = D - R = (13936, 12771),  |axis| = 18903

u = axis / |axis| = ( 0.7373,  0.6756)     along the diagonal
n = perpendicular  = (-0.6756,  0.7373)     across it

depth(p)   = ((p - R) · u) / 18903      0 = Radiant fountain, 1 = Dire fountain
lateral(p) =  (p - R) · n               signed units off the mid diagonal

# make it team-relative so both sides are comparable
own_depth  = depth        if Radiant else 1 - depth
own_lateral= lateral      if Radiant else -lateral

own_depth runs 0 at your own fountain to 1 at the enemy's — a single number for "how far forward am I", directly comparable across teams. own_lateral is roughly ±9400 at the map corners and gives us the lane.

Zones (proposal — needs validating)

The 2500 threshold is a guess and should be set from the data: plot the distribution of own_lateral during the first 10 minutes, when players are reliably in lanes, and pick the cut that separates the three modes. A fourth "jungle / river" zone is a natural extension if the three-way split proves too coarse.

Deaths are a mask, not a feature. A death shows up cleanly in position data — the player teleports to their fountain and sits there. That makes deaths cheap to detect without the combat log, which is useful. But death count is a component of KDA, and the leakage guide is explicit that outcome signals must not enter the movement feature set. So is_dead is used only to exclude dead time from movement statistics, exactly as the guide prescribes for m_lifeState.

5. Layer 2 — what the model actually sees

One row per player per match. Bucketed features are computed for each of the nine zone × phase combinations; match-level features are computed once. All movement statistics exclude time spent dead.

The subtle one: speed is partly bought with gold. The earlier feature review excluded m_iMoveSpeed because boots are purchased with gold, which would smuggle economy into a movement-only model. Observed velocity has the same problem — a richer player simply moves faster. We should either normalise speed within phase, treat speed features as a documented caveat, or run the ablation both ways and report the difference. Leaving it unexamined would undermine the movement-vs-economy comparison the whole project rests on.
Dimensionality. Seven bucketed features × 9 buckets plus 6 match-level ones is about 69 features per player. With 500 matches that is 5,000 player rows — but only 500 independent matches, so the effective sample is far smaller than the row count suggests. Expect to need regularisation and feature selection, and to report performance with grouped cross-validation by match_id.

6. The leakage risk we have to design around

The other nine players are a shortcut to the label. Matchmaking puts similar-skill players together, so the people around you are strong evidence of your own rank — before anyone looks at how you move. Any feature that reflects where teammates or opponents are lets the model read the lobby's skill level instead of the player's.

The pilot lets us size this exactly. Player rank varies within a match with a standard deviation of about 7.5 tier units, and across matches with about 13.6. So:

Source of variation in a player's rankShare
Which match they were in (the lobby's overall level)76%
Who they are, relative to the others in that same match24%

A model that learns nothing about individuals but manages to infer "this is a Legend-level lobby" already has three quarters of the signal. And the relational features in this spec — dist_team_centroid, dist_nearest_ally, dist_nearest_enemy, allies_within_1500, enemies_within_1500 — are all computed from the other nine players' positions, which is precisely the information that identifies the lobby.

This is not label leakage in the textbook sense; the label never appears in the features. But the consequence is the same. We would report that movement predicts skill, when much of the performance came from reading the skill level of everyone else in the game. It is the same confounding logic as the region argument, with a variable we cannot simply filter out.

The control that settles it

Teammate-only negative control. Build a second model that predicts the target player's rank using only the other nine players' features — the target's own movement excluded entirely. That model has no individual signal by construction, so whatever it scores is the size of the shortcut. If the full model beats it by a wide margin, the relational features are earning their place. If the two land close together, the full model is mostly reading the lobby and we have to say so.

This is cheap to run, needs no extra data, and it converts an unfalsifiable worry into a number we can report. It should be a required row in the results table alongside the economy-only and movement-only baselines the mentor asked for.

Two other mitigations

  • A self-only feature set. Features that depend on nothing but the target's own trajectory — own_depth, speed, path_efficiency, map_coverage, rotations, time_share per zone — are immune to this shortcut. Running the model on self-only features gives a clean lower bound, at the cost of dropping the team-spread hypothesis from the proposal.
  • A within-match setup would remove it entirely, but that changes the modelling task rather than the feature table, so it is written up in Feature Spec — Extensions and is not assumed anywhere in this document.

Splitting rules this implies

  • Group by match_id, not only by account_id. Two players from the same match in different folds share the entire lobby context.
  • Deduplicate by account_id as already agreed, so no player appears in both folds.

7. Open decisions

Zone thresholds. Is 2500 units the right cut for mid lane? Validate against the 20 parsed matches before committing. Do we want a fourth jungle/river zone?
Phase boundaries. Fixed times now, or wait for tower events and use them? Fixed times can ship today.
Speed and economy. Do we keep speed features, normalise them, or drop them to keep the movement-only claim clean?
Per-role handling. A support and a carry move very differently, and role is not in our data. Position-based role inference is possible from laning-phase behaviour, but is itself a modelling task. Ignoring it means part of the "skill signal" may be role signal.
Relational features: keep, or go self-only? This is the decision section 6 forces. Running the teammate-only control first turns it into an evidence-based call rather than a judgement call.
Professional play. The proposal's third research question compares amateur and professional play, but we are collecting only public ranked matches. Pro replays come from a different endpoint and do not expire. Either we add them or we narrow the question.

8. Immediate next step

Before writing any feature code, run one validation pass on the 20 already-parsed matches: transform the coordinates, plot own_lateral for the first ten minutes, and check that it separates into three clear lane modes. If it does, the zone rule is settled and the rest of this spec is straightforward implementation. If it does not, the zone definition needs rethinking before anything is built on top of it.
